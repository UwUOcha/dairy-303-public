# Между парами — платформа расписания

Одна установка — один университет: собственные база, сайт, Telegram/VK-боты и
пользователи. Для другого вуза нужны собственный HTTP-адаптер, профиль и ключи.
Исходники общей платформы менять не требуется.

```text
API вуза → адаптер → HTTP/JSON v1 → raspd → botd (Telegram/VK)
                                   │    → webd (сайт/PWA + админка)
                                   └── SQLite этой установки
```

Ядро хранит расписание локально, обнаруживает изменения и продолжает отвечать
при недоступности адаптера. Сайт и боты обращаются к ядру по Unix-сокету.
Адаптер не получает базу экосистемы, пользователей или токены ботов.

**Хотите подключить свой вуз?** Вам нужно написать только адаптер — небольшой
веб-сервер, который достаёт расписание вашего вуза и отдаёт его в общем JSON-формате.
С чего начать и как выглядят ответы — в разделе
[«Коротко: что нужно написать»](docs/ADAPTERS.md#коротко-что-нужно-написать).

## Запуск

```sh
docker compose up --build -d adapter raspd webd
```

Откройте http://localhost:8306. По умолчанию используются вымышленные данные
независимого Python-адаптера и `profiles/example.json`. Это полный импорт через
API ядра. Без Docker запустите в отдельных терминалах `make run-adapter-json`,
`make run-rasp`, `make run-web`.

Для своего вуза скопируйте профиль примера, задайте `RASP_PROFILE_FILE` в `.env`,
реализуйте [контракт адаптера](docs/ADAPTERS.md), замените его образ/сборку в Compose
overlay и проверьте `PROVIDER_URL=http://localhost:8310 make check-adapter`.
Ключи API вуза передавайте адаптеру, токены Telegram/VK — только botd.
Для ботов создайте `deploy/bot.env`, заполните ссылки в профиле и запустите
`docker compose --profile bots up -d botd`. Для внешнего доступа настройте HTTPS proxy.

## Структура

| Каталог | Содержание |
|---|---|
| `pkg/provider` | Общий HTTP-контракт, клиент, обработчик и валидация |
| `internal/providerclient`, `importdata` | Импорт нормализованных данных |
| `internal/store`, `syncer`, `schedule`, `api` | Ядро и база |
| `internal/botcore`, `tg`, `vk` | Сценарии ботов |
| `internal/web`, `admin`, `profile` | Сайт, встроенная админка, профиль |
| `examples/adapter-json` | Независимый адаптер на Python |
| `profiles/example.json` | Настройки вымышленной установки |

```sh
make all
go test -race ./...
```

Проверка границ охватывает исходники **и тесты** платформы. Она запрещает зависимость
от реализации конкретного вуза. OpenAPI генерируется из типов контракта и проверяется
на соответствие. Для тестов нужны Go по `go.mod`, Python 3 и Node.js.

`make export-platform OUTPUT=dist/platform` создаёт отдельное дерево исходников по
явному списку: без локальных баз, env-файлов, истории Git и вузовских интеграций.
Повторный экспорт поддерживает `REPLACE=1` для неизменённого результата;
`MODULE=example.org/university/schedule` задаёт путь модуля будущего репозитория.
Экспорт сам ничего не отправляет. Платформа — AGPL-3.0-only, библиотека
`pkg/provider` — MIT; см. [лицензирование](LICENSING.md) и [границу публикации](docs/PUBLICATION.md).
