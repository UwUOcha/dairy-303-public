# Архитектура платформы

Одна установка обслуживает один университет. У каждой установки собственные
база, пользователи, сайт, боты, ключи и профиль. Общего сервиса для нескольких
вузов, выбора арендатора в запросах и разделения вузов внутри одной базы здесь нет.
Переносимость означает возможность использовать тот же код платформы в другой
независимой установке.

## Как проходит запрос

```text
                         сеть Docker: HTTP/JSON v1
API университета ← адаптер ←──────────────────────── raspd
                   │                                  │
             своё состояние                     SQLite установки
             (если требуется)                         │
                                          Unix-сокет  ├── botd → Telegram/VK
                                                      └── webd → HTTPS proxy
                                                          сайт + /admin/
```

Стрелка к источнику означает запрос: ядро само опрашивает адаптер. Адаптер не
рассылает события ядру, не обслуживает пользователей и не отправляет уведомления.
Он переводит данные своего вуза в [общий контракт](ADAPTERS.md).

`raspd` хранит локальную копию расписания, обновляет её по расписанию, сравнивает
версии и формирует данные для уведомлений. `botd` ведёт диалоги и отправляет
сообщения. `webd` обслуживает сайт, вход и встроенную панель наблюдения.
Пользовательские сервисы обращаются к ядру через Unix-сокет; базу расписания
открывает и изменяет только ядро. Панель имеет отдельную базу истории метрик.

Обычно нажатие кнопки сайта или бота читает уже сохранённое расписание. Если
нужный месяц отсутствует или устарел, ядро может запустить догоняющий импорт.
Пользовательский запрос ждёт источник не более шести секунд, затем получает
сохранённую копию, если она есть. Общая загрузка месяца может продолжиться после
этого: одинаковые одновременные запросы объединяются, отмена одного клиента не
прерывает работу для остальных. Поэтому HTTP 200 сайта не доказывает, что новые
данные успешно импортированы; нужно проверять свежесть и результат синхронизации.

## Что изменилось

| Область | Прежняя установка | Текущая платформа |
| --- | --- | --- |
| Получение расписания | Ядро непосредственно обращалось к API конкретного вуза | Ядро знает только контракт HTTP/JSON v1 |
| Разбор ответов и особенности источника | Клиент и правила находились среди внутренних пакетов проекта | Собственный сервис адаптера |
| ID сущностей | Предполагались числовые идентификаторы исходного API | Внешние строковые ID сопоставляются с внутренними ID ядра |
| Тексты и оформление | Вузовские подписи и ссылки были распределены по коду | Профиль, заменяемые изображения и отдельная интеграция |
| Новый вуз | Требовалось менять код получения данных и искать привязки в интерфейсе | Собственный адаптер, профиль, ключи и конфигурация запуска |
| Панель наблюдения | Отдельный процесс admind, оформление и ограничение по IP | `/admin/` в webd, тема сайта, проверка аккаунта и IP |
| Публикация | Общий репозиторий включал всю установку | Экспорт платформы по явному списку без интеграции и истории Git |

HTTP/JSON выбран для доступности реализации на любом языке, простого просмотра
ответов и независимого выпуска сервисов. Здесь нет высокочастотного потока,
для которого обязательны бинарный транспорт и streaming gRPC. Дополнительная
сериализация и сетевой переход существуют; они происходят при импорте и обычно
не добавляются к каждому пользовательскому чтению. Переход сам по себе не обещает
ускорения по сравнению с прямым вызовом API из монолита.

## Границы ответственности

| Слой | Что находится внутри | Чего он не должен знать |
| --- | --- | --- |
| `pkg/provider` | Версия протокола, типы, HTTP-клиент/обработчик, валидация | Устройство API конкретного университета |
| `internal/providerclient` | Проверка источника, перевод внешних ID, нормализованный импорт | Токены и нестандартные поля исходного API |
| `internal/store`, `syncer`, `schedule`, `api` | Хранилище, обновления, история, пользователи, расписание | Алгоритмы поиска вузовских дубликатов |
| `internal/botcore`, `tg`, `vk` | Общие диалоги и доставка сообщений | Формат API университета |
| `internal/web`, `admin` | Интерфейс, вход, панель, HTTP-границы доступа | Прямая работа с API университета |
| `internal/profile` | Названия, ссылки, учебные периоды, темы, настройки установки | Секретные токены |
| Адаптер | Загрузка, разбор, нормализация, лимиты API и специфичные правила | Пользователи и база платформы, токены ботов |

Не каждый адаптер обязан иметь базу. Она нужна, если источник требует устойчивого
сопоставления ID, кэширования или исторических сведений. Эта база принадлежит
адаптеру и не заменяет хранилище ядра.

## Сохранность данных

Источник имеет постоянный `source`, записанный в базе. Случайно подставить адаптер
другого вуза поверх существующих пользователей нельзя: ядро отклонит несовпадение.
Внешние строковые ID сохраняются в таблице соответствий; имена и ФИО сами по себе
не доказывают идентичность. Общие занятия нескольких групп имеют отдельные связи
с каждой лентой и не исчезают из остальных при удалении из одной группы.

Месяц записывается транзакционно вместе с метаданными импорта. Ошибка, неполный
или неопубликованный ответ не должны стирать прежнее расписание. Полный
опубликованный пустой ответ, напротив, означает подтверждённое отсутствие занятий.
Ответ адаптера должен честно различать эти случаи: ядро не может восстановить
знание, которое адаптер неправильно обозначил как достоверное.

Для миграции прежних числовых ID есть явный режим `RASP_IMPORT_LEGACY_IDS=true`.
Он нужен существующей установке, не новому вузу. Первая импортированная версия
каждого месяца становится базовой без массового уведомления о смене представления
данных. Последующие реальные изменения обрабатываются как обычно.

## Доступ и изоляция

Ключи API университета передаются только его адаптеру. Токены Telegram/VK — только
боту. Служебный Bearer-токен между ядром и адаптером — отдельный секрет. Адаптер
не публикует порт наружу в базовом Compose; при разнесении машин нужен защищённый
транспорт. Разделение сервисов ограничивает доступ к данным, но не даёт абсолютной
изоляции ресурсов: процессы по-прежнему делят CPU, память и диск одного хоста.

Админка проверяет и аккаунт из сессии, и клиентский IP при каждом запросе.
Это две проверки доступа, а не классическая двухфакторная аутентификация с OTP:
IP не является независимым секретом. Политика доверия к proxy и поведение при
завершении сессии описаны в [ADMIN.md](ADMIN.md).

## Что остаётся ограничением

- Платформа моделирует группы, подгруппы, занятия, преподавателей и учебные периоды.
  Оценки, оплата, зачисление и произвольные процессы вуза не появляются автоматически.
- Интерфейс и основные сценарии русскоязычные. Профиль меняет бренд и выбранные
  тексты, но не является полной системой локализации или конструктором интерфейса.
- Контракт v1 имеет ограничения: до 31 даты на запрос, без пагинации, ответ до
  32 MiB, время занятия в пределах одних суток. Особые случаи описаны в ADAPTERS.md.
- API вуза может не различать пустое расписание и ещё не опубликованное. Такой
  недостаток источника нужно документировать в адаптере.
- SQLite и Unix-сокет предполагают одну локальную установку с единственным
  писателем. Горизонтальное масштабирование ядра и высокая доступность не реализованы.
- Независимость проверяется тестами и отдельным Python-примером. Это подтверждение
  границы модулей, но не доказательство совместимости со всеми реальными вузами.
- Изменения семантики обязательных полей требуют новой основной версии контракта;
  независимые выпуски ядра и адаптера всё равно должны соблюдать совместимость.
