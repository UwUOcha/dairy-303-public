# Своя установка для другого университета

Результат — независимые сайт, боты и база одного вуза. Оператор первой установки
не получает пользователей или ключи второй. Общими остаются исходники платформы
и HTTP-контракт адаптера.

## 1. Получить платформу

Из репозитория, содержащего университетские интеграции, выполните:

```sh
make export-platform OUTPUT=dist/my-platform
cd dist/my-platform
cp .env.example .env
```

Каталог назначения должен отсутствовать. Скрипт копирует исходники по явному
списку, исключая интеграции, рабочие env-файлы, базы, `run/` и `.git`. Общая
документация входит в экспорт; помеченные разделы конкретной установки удаляются.
Экспорт не меняет Git-историю исходного репозитория и не публикует новый репозиторий.
Платформа распространяется под AGPL-3.0-only, `pkg/provider` — под MIT; см. [LICENSING.md](../LICENSING.md).

Сначала можно запустить вымышленную установку:

```sh
docker compose up --build -d adapter raspd webd
```

Сайт доступен на `http://localhost:8306`. По умолчанию пример открыт для чтения,
боты не запускаются. Для настоящего вуза используйте новую базу/новый Compose-проект,
а не меняйте источник в уже заполненном демонстрационном томе.

## 2. Реализовать адаптер

Начните с раздела [«Коротко: что нужно написать»](ADAPTERS.md#коротко-что-нужно-написать), затем прочитайте остальной [ADAPTERS.md](ADAPTERS.md) и OpenAPI. Адаптер — отдельный HTTP-процесс
на удобном вам языке. Python-пример показывает минимальную реализацию без
зависимости от Go. Вместо вымышленного JSON получите данные своего университета
и приведите их к общим сущностям.

Минимум: сведения об источнике, полный каталог групп и расписание группы за
диапазон дат. Расширенный справочник преподавателей необязателен. Реализуйте
устойчивые ID, правильную обработку пустых/неполных ответов, часовой пояс,
ограничение частоты запросов и ошибки. Не переносите особенности своего API в ядро.
Свою базу добавляйте только при необходимости; доступ к базе платформы не нужен.

Соберите свой образ, слушающий `:8310`. Для локальной проверки запущенного адаптера:

```sh
PROVIDER_URL=http://127.0.0.1:8310 make check-adapter
```

При включённом служебном токене передайте также `PROVIDER_TOKEN` через окружение.
Проверка охватывает одну активную группу и объявленные возможности, поэтому
дополнительно проверьте реальные сложные группы и повторные обновления.

## 3. Настроить установку

Скопируйте `profiles/example.json` в `profiles/my-university.json` и заполните
название, домен, часовой пояс, учебные периоды, ссылки на ботов и административные
ID. Поля и изображения описаны в [PROFILES.md](PROFILES.md). В `.env` укажите:

```dotenv
RASP_PROFILE_FILE=./profiles/my-university.json
CORE_IMAGE=university-schedule:local
ADAPTER_IMAGE=my-university-adapter:local
RASP_IMPORT_LEGACY_IDS=false
```

Задайте случайный `PROVIDER_TOKEN`, одинаковый для ядра и адаптера. Токены API
университета положите в `deploy/my-adapter.env`. Ключи Telegram/VK — отдельно в
`deploy/bot.env`, взяв за основу пример. Не добавляйте эти файлы в Git.

Для своего готового образа создайте `compose.university.yaml`:

```yaml
services:
  adapter:
    image: ${ADAPTER_IMAGE}
    env_file: [deploy/my-adapter.env]
```

Базовый Compose содержит сборку демонстрационного адаптера. При использовании
этого overlay запускайте готовые образы с `--no-build`: так пример не будет
случайно собран под именем вашего образа. Если хотите собирать адаптер через
Compose, переопределите и `build.context`, и `build.dockerfile` под его исходники.

Пример отдельного рабочего проекта:

```sh
# Собрать общую платформу локально; адаптер уже собран отдельно.
docker build -t university-schedule:local .
docker compose -p my-university -f compose.yaml -f compose.university.yaml config --quiet
docker compose -p my-university -f compose.yaml -f compose.university.yaml up --no-build -d adapter raspd webd
# После проверки данных и заполнения deploy/bot.env:
docker compose -p my-university -f compose.yaml -f compose.university.yaml --profile bots up --no-build -d botd
```

Демонстрационный сайт на том же хосте перед этим остановите: порт 8306 общий.
Имя проекта, набор overlay и файлы конфигурации используйте одинаковые при
последующих командах. Для внешнего доступа настройте HTTPS reverse proxy.
Админка требует входа через настроенного бота даже при открытом чтении сайта;
допуск и настройка proxy описаны в [ADMIN.md](ADMIN.md).

## 4. Проверить до допуска пользователей

Проверьте не только запуск процессов: реальные группы и подгруппы, общее занятие
нескольких групп, отмену/перенос занятия, повторный импорт, отсутствие ложных
уведомлений и работу при недоступном API. Отдельно проверьте вход, настройки
пользователя, права админки и время рассылок в нужном поясе. Новая установка
не должна зависеть от наличия исходников прежнего адаптера.

```sh
make vet test test-ui check-boundaries check-schema build
```

Тесты платформы включают отдельный Python-процесс адаптера и сценарии сайта/бота.
Они не заменяют проверку вашего преобразования реальных данных университета.
Проведите ограниченный пробный обход до полного ночного запуска; правила
безопасного стенда и резервных копий — в [OPERATIONS.md](OPERATIONS.md).

## Что действительно может потребовать изменения ядра

Если данные укладываются в существующие сущности, достаточно адаптера, профиля
и конфигурации. Если нужен новый продуктовый сценарий — например, оценки,
зачисление или модель расписания, не выражаемая контрактом v1, — его нужно
проектировать отдельно. Для таких изменений сначала согласуйте общий контракт
и поведение платформы; не добавляйте специальные ветки по имени университета.
