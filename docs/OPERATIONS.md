# Эксплуатация платформы

## Проверять живость и свежесть отдельно

`docker compose --profile bots ps` показывает состояние сервисов.
`raspd -health` и HTTP `/health` проверяют работоспособность процесса/API.
Недоступный университет не делает локальное расписание бесполезным, поэтому
успешная проверка здоровья не гарантирует успешного последнего импорта.

Проверяйте журналы ядра и адаптера, время последнего завершённого обхода, число
ошибок, длительность и свежесть нужного месяца. При таймауте сайт способен вернуть
сохранённые данные с HTTP 200; это ожидаемое поведение, а не доказательство
доступности источника. Панель `/admin/` объединяет статистику и историю метрик.

```sh
docker compose logs --since=30m --tail=100 raspd adapter
# Команда завершается после одного замера:
docker stats --no-stream
```

Не выводите `docker inspect` целиком и развёрнутый `docker compose config` в общие
журналы: окружение содержит секреты. Для проверки конфигурации используйте
`docker compose config --quiet`.

## Производительность

Пользовательский путь обычно читает локальную SQLite-базу. Сеть и разбор ответов
источника расходуются на синхронизацию. Добавление адаптера даёт сетевой переход,
JSON-кодирование/декодирование, отдельный процесс и, при необходимости, своё
хранилище. Это цена разделения ответственности, не бесплатное ускорение.

Сравнивайте нагрузку на одинаковом числе групп, месяцев и занятий. Различайте:

- время ожидания запроса к университету и время CPU;
- простой сервиса, обход активных групп и полный обход;
- локальный benchmark SQL и измерение всей установки;
- CPU-секунды за интервал и процент одного ядра.

У сервиса, который ждал сеть две секунды и считал 20 мс, не было двух секунд
процессорной работы. Процент в `docker stats` относится к одному логическому ядру:
100% означает одно полностью занятое ядро; показатель может превышать 100%.

Непрерывная высокая нагрузка после ожидаемого завершения обхода требует диагностики.
Сначала найдите конкретный процесс, проверьте число запросов, повторы, план SQL
и состояние циклов. Ограничение CPU ограничивает воздействие ошибки, но не устраняет
её и может увеличить длительность обхода. Учитывайте индексы обратных связей:
их отсутствие способно превратить короткую очистку после каждого месяца в
многократный полный перебор таблиц.

Обработка цепочек замен групп заканчивается, когда целый проход никого не
перемещает. Заведомо неизменившееся состояние не должно повторно обрабатываться
по числу всех правил. Проверяются и короткий путь, и цепочки, требующие нескольких
проходов. Для уже завершённых переносов есть
`BenchmarkSettledGroupReplacements` в тестах хранилища.

## Пробные установки

Проверяйте изменения на отдельной копии, под отдельным именем Compose-проекта,
с отдельными томами и без токенов ботов. Не открывайте одну рабочую базу двумя
ядрами. Для точечного импорта задайте `raspd -background-sync=false`.

Такой стенд должен иметь независимую от SSH остановку по времени, например
systemd `RuntimeMaxSec` вместе с `ExecStopPost`, который останавливает только его
контейнеры. Shell trap полезен дополнительно. Одного лимита CPU и закрытия
терминала недостаточно. После прогона проверьте фактическое завершение контейнеров.

Отключение фонового режима не отключает догоняющие запросы API. Выбирайте
конкретные группы и диапазоны. Тесты админки должны проверять разрешённую пару
аккаунт/IP, неподходящий аккаунт, неподходящий адрес, заголовки proxy и выход.

## Резервные копии и обновление

База содержит не только восстанавливаемое расписание, но и пользовательские
настройки, доступ, сессии, ключи, очередь и историю. Сохраняйте её согласованным
SQLite backup API либо после остановки писателя. Копирование живого `schedule.db`
без WAL теряет данные; архивирование файлов базы и WAL по очереди во время записи
тоже не гарантирует согласованный снимок.

Существующий `make backup` архивирует том как файлы: применяйте его только после
остановки сервисов, которые могут писать в базу. Для живой установки нужен SQLite
backup API. Отдельно сохраняйте базу истории панели, профиль, конфигурацию proxy,
env-файлы и точные версии образов. Секретные резервные копии не включайте в Git.

Перед рабочей миграцией остановите бот и входящие пользовательские изменения,
затем писателя базы и сделайте свежий снимок. Пробную базу нельзя использовать
вместо текущей: за время проверки пользователи могли изменить настройки.
После обновления сначала проверьте ядро, данные, сайт и доступ; затем возобновляйте
бота. Не запускайте бот со своей рабочей учётной записью одновременно в двух
установках.

Откат к бинарнику, который не понимает новую схему, требует прежней базы вместе
с прежним образом. Предварительно сохраните текущее состояние и оцените изменения
пользователей после переключения. Один откат контейнерного образа не откатывает SQL.

## Сбои, которые нужно учитывать

| Ситуация | Последствие и действие |
| --- | --- |
| Адаптер или API вуза недоступен | Сохранённое расписание остаётся доступным, новые изменения не приходят; проверять свежесть |
| Ошибочный пустой успешный ответ | Может удалить занятия из указанной ленты; исправить полноту ответа в адаптере |
| Смена ID у источника | Риск дубликатов и лишних изменений; адаптер должен сохранять устойчивые соответствия |
| Недоступно ядро или его сокет | Сайт и бот теряют API, доступ к админке не обходится; восстановить ядро |
| Сменился IP пользователя | Админка отказывает до обновления списка разрешённых адресов |
| Пересоздан proxy с новым адресом | Проверить точный `WEB_TRUSTED_PROXIES`; не расширять доверие на всю сеть автоматически |
| Не обновляется расширенный справочник | Преподаватели из занятий и сохранённые сведения продолжают работать; проверять возможности и лимиты адаптера |
